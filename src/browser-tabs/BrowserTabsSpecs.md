# Browser tabs

The Switch action is hidden for shortcuts that switch on modifier release. An empty footer is removed so the list uses its space. Refresh and Automation controls remain available when needed. Keep-open shortcuts and menu invocation retain the Switch action. The window panel follows the same rule while modifier release is active; entering search keeps the panel open and restores its action.

Each shortcut has a Search toggle below Switch between. Search defaults to enabled for both targets. Disabling it hides the search header, stops filtering, and reclaims the header's height. Tab and arrow navigation, Return, Escape, modifier release, and switching still work. The browser Refresh button moves to the footer when search is disabled; Command-R remains available. Both launcher panels center the search field in the same 56-point header, with a 6-point gap between the field and the first row.

Browser tabs are a target in Settings > Controls > each shortcut's Switch between selector. Choosing Windows shows its filtering, appearance, and ordering options. Choosing Browser tabs shows browser scope (Safari and Chrome, Safari, or Chrome), release behavior, size, and theme. Switching targets preserves each target's stored options. The existing Control-Option-Tab shortcut is migrated into a browser-tab shortcut slot without changing window bindings. An installation with all nine slots in use retains its legacy binding in Additional controls until a slot is available.

Browser tabs default to Keep open after releasing modifiers. The Switch option instead cycles while the trigger modifiers are held and activates the selection when they are released. Return and keypad Enter also activate immediately; Escape dismisses without switching. Releasing during collection defers activation until the current collection completes. Errors keep the panel open. Repeated shortcut presses during collection retain their selection advances. Menu invocation keeps the panel open and uses the first browser shortcut's scope and appearance. Artificial key repeat uses the same timing and physical-key checks as window shortcuts, with its initial-delay grace measured from when tabs become available. Only the selected browsers receive collection and permission requests.

Both the browser panel and the window switcher's Titles appearance use a shared launcher design inspired by [Tinycast](https://github.com/abue-ammar/tinycast): a rounded glass surface with a dark or light tint, a full-width borderless search field, compact single-line rows, neutral selection fill, muted trailing app/browser labels, and a footer action capsule labeled Switch. The browser panel has no redundant section subtitle or tab-count label. Both panels use the same maximum 750 point width and shared size-dependent icon and font metrics. Height grows to fit all rows until it reaches the screen's usable height; longer lists then scroll. Filtering keeps the browser panel's height stable. The browser search is visible immediately. Command-R refreshes; a row's tooltip includes its address. Permission and collection errors display status and Automation controls without hiding successful results. The window switcher keeps its existing hold-to-cycle and search-mode behavior.

- Collect only running supported browsers. Request Automation consent through browser scripting when the user summons or refreshes the panel. Permission denial remains distinct from a successful empty list.
- Return structured JSON, preserving punctuation, Unicode and linefeeds in titles and URLs. No browsing data is logged or written to a script file.
- Request browser Automation consent on the serial background queue before launching osascript. Waiting for a human response is outside the eight-second script timeout. Denied browsers produce issues while permitted browsers still return tabs.
- Keep the panel visible when an Automation dialog takes focus during collection or activation. Restore search focus when the operation finishes. Escape or the close button still dismisses immediately, and a stale asynchronous result cannot reopen the panel.
- Script execution runs in a child osascript process on a serial background queue. Bound the process lifetime to eight seconds after consent. Summoning paints before starting collection.
- Keep successful results when the other browser fails. Show its permission/error status alongside available tabs. Refresh is explicit; there is no background polling.
- Chrome activation resolves the native tab ID across windows, including a tab moved after the snapshot. Safari resolves the window ID and position and validates the title and URL; reject a changed position. Safari does not provide a stable tab ID, so identical tabs cannot be distinguished after a reorder.
- Revalidate the browser process before activation. Never open a URL to approximate selecting a missing tab. A stale tab produces an explanatory message and can be refreshed.
- Search matches every whitespace-separated query term against title, URL, browser name or discovered profile name. Preserve the selected tab by identity when refreshing/filtering where possible.
- Browser queries include whatever windows the browser exposes to its scripting interface; private-window visibility and profile completeness depend on the browser. Firefox and extension-based collection are outside this version.

The permissions window offers optional browser Automation setup for running Safari and Chrome instances. It uses the same permission API and serial collector queue as tab collection, without launching scripts. Skipping or completing setup is remembered, so later launches do not require a running browser or Automation consent.

## Chrome profile labels

Normal Chrome tabs show `Chrome · <profile>` when their window matches exactly one accessibility window. Search, tooltips, and accessibility labels include the profile name. Labels truncate at 180 points so long names leave room for the tab title. Labels do not affect tab identity or activation.

Collection displays tabs before scheduling optional profile reads through the AX scan lane. Activation never waits for these reads. Each Chrome process gets a 400 ms read budget and a 150 ms AX messaging timeout. Missing access and unsuccessful reads leave tabs unlabeled without a collection error. Profile detection requires no permission prompt, profile-file access, disk persistence, or polling.

Chrome scripting window IDs differ from native CGWindowIDs. Match geometry within one point and the scripted active-tab title. Accept only a unique match in both directions. Equal geometry and titles, duplicate IDs, changed active titles, moved windows, missing metadata, and modal titles remain unlabeled. Failed optional scripting metadata invalidates that process's window metadata. Failed AX reads invalidate the whole AX inventory, so a partial inventory cannot establish uniqueness.

Private and guest windows never inherit a named profile. Chrome omits its profile suffix for a single profile. The recognized format is `<active title> - Google Chrome - <profile>`, from Chromium's `IDS_ACCESSIBLE_WINDOW_TITLE_WITH_PROFILE_FORMAT`. Unrecognized localized formats stay unlabeled.

Profile updates run after rendering, on a subsequent main-runloop turn. A separate refresh generation rejects late results after dismissal, activation, or a newer refresh. Filtering preserves the selected tab's identity when labels arrive.
